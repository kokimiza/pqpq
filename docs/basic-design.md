# pqpq 基本設計書

本書は、ターミナルとWebブラウザから同じ部屋で対戦できるリアルタイムレーシングゲーム `pqpq` の初期実装に向けて、5クレート構成、画面、共有シミュレーション、通信、データ、運用および受入条件を定義する。読者はネイティブ・Web・サーバの実装担当者と検証担当者とする。

正しいゲーム状態は単一サーバが決定し、すべてのプレイヤー情報・部屋・結果をメモリ内だけで管理する。ターミナルはNative QUIC、ブラウザはWebTransport over HTTP/3で同じサーバへ接続する。シミュレーションをRustで共有し、ブラウザではWebAssemblyとして実行する。

## 1 設計の前提と範囲

### 1.1 要件として確定している事項

- ネイティブクライアント、WebAssemblyを含むWeb配布物、サーバ1バイナリ、サーバVM1台で構成する。
- Cargo Workspace内のクレートはclient、server、protocol、sim、webの5つとする。
- クライアントの起動形式は `pqpq <username> <room_id>` とし、必須引数は2つだけとする。
- ブラウザはURLから参加画面を開き、ユーザ名と部屋IDだけを入力する。WebとCUIは正式な同等のクライアントとする。
- Windows・Linux・macOSのターミナルとWebブラウザが同じ部屋で競走できるようにする。
- ユーザ名は表示名であり、重複を許可する。本人認証・アカウントは設けない。
- 存在しない部屋への参加時に、その部屋を作成する。最後のプレイヤーが退出したら削除する。
- ネイティブ通信はCloudflare quicheを使用し、CUI描画にはRatatuiを使用する。実行基盤のTokioと端末操作のCrosstermは本基本設計で継続採用する。
- ブラウザはWebTransportを使い、通信形式はprotocol、物理・状態遷移はsimで共有する。
- サーバのゲーム更新は30Hz、クライアント描画は60FPSを目標とする。
- コース1種類、3周、同一車両性能、衝突・順位あり、アイテム・NPCなしとする。
- 自車予測、サーバ状態への補正、他車の補間を実装する。
- DB、外部キャッシュ、ユーザデータ保存、戦績保存、リプレイ保存、セッション復元を設けない。
- サーバ停止による全ゲーム状態の消失を許容し、HA・フェイルオーバーは設けない。

初期利用は要件どおり1〜3人を想定する。通常レースは本書の設計判断で2人以上とし、1人での開発検証も可能にする。人数を4人に固定せず、10人・20人の接続試験を可能にする。

### 1.2 基本設計で補う事項

以下は上位要件に明記されていないため、本書で採用する初期方針である。チューニング対象の数値は保証値ではない。

| 項目 | 採用する方針 |
| --- | --- |
| 開始条件 | 2人以上が入室し、走行予定者全員がReadyになったら3秒のカウントダウンを開始する |
| 1人での検証 | 開発用の起動時設定で最少開始人数を1に変更可能とする |
| 途中参加 | Racing中は観戦者として入室する。走行中のレースへ車両は追加しない |
| 終了後の参加 | Finished中は結果を閲覧する。自動的に次のレースを開始しない |
| 再レース | 初期版は全員退出後に部屋を作り直す。部屋内の再戦機能は対象外 |
| 制限時間 | Racing開始からシミュレーション時間10分で未完走者をDNFとして終了する |
| 容量制限 | 初期値は1部屋32接続、サーバ全体128接続、64部屋。起動時設定で変更可能とする |
| 通信設定 | NativeはALPN `pqpq/1`、WebTransportはHTTP/3のALPN `h3`。ゲームプロトコル版は共通の1 |
| Web配信 | pqpq-server内のHTTPS静的配信機能からHTML・JS・WASMを配信。常駐サーバを増やさない |
| 配信頻度 | 入力送信とSnapshot配信は30Hzを初期値とする |

観戦は途中参加を成立させるための最小限の表示であり、専用の観戦者検索・カメラ操作・観戦用サービスは設けない。容量制限はメモリ保護のための上限であり、この人数で30Hzを保証するものではない。

## 2 システム構成

### 2.1 配置構成

```text
Terminal / pqpq-client
  Ratatui + pqpq-sim
         │ Native QUIC / ALPN pqpq/1 / UDP 4433
         ▼
┌──────────────────────────────────────────────────────┐
│ pqpq-server                    単一VM・単一プロセス    │
│ Native adapter ─┐                                    │
│                 ├─ Reliable/Unreliable ─ Room管理     │
│ Web adapter ────┘                      pqpq-sim      │
│ HTTPS静的配信                          30Hz更新      │
└──────────────────────────────────────────────────────┘
         ▲                             │ HTML/JS/WASM
         │ WebTransport / h3 / UDP 443 │ HTTPS / TCP 443
         │                             ▼
Browser / pqpq-web + web/
  参加フォーム + Canvas + pqpq-sim/WASM
```

本番相当環境は要件どおりOCI大阪リージョンの単一VMを想定する。OSはLinuxを設計上の第一候補とし、VMの形状・CPU・メモリは実測後に決める。Web用の静的配信も同じサーバプロセスが担当する。WebSocketやHTTPポーリングによるゲーム通信、外部の中継バックエンド、ロードバランサー、DBサーバは追加しない。

初期設計ではNativeとWebTransportでUDPリスナーを分け、別のtransport adapterから同じ部屋管理へ渡す。上図のポートは本番用の初期案とし、開発時はNative UDP 4433、WebTransport UDP 8443、HTTPS TCP 8443を使用する。同じ番号のTCP/UDPは用途の異なるリスナーとして扱う。

### 2.2 クレート構成と依存

| クレート | 成果物 | 責務 | 主な依存予定 |
| --- | --- | --- | --- |
| `pqpq-client` | 実行ファイル `pqpq` | 引数、接続、キー入力、予測・補正・補間、CUI描画 | protocol、sim、Tokio、quiche、Ratatui、Crossterm |
| `pqpq-server` | 実行ファイル `pqpq-server` | Native/Web接続、部屋、進行・順位の確定、配信、HTTPS静的配信 | protocol、sim、Tokio、quiche、選定するWebTransport・HTTPS実装 |
| `pqpq-protocol` | ライブラリ | 通信型、識別子、メッセージ形式、シリアライズ、プロトコル制約 | 選定するシリアライズライブラリのみ |
| `pqpq-sim` | ネイティブ・WASM対応ライブラリ | InputState、CarState、コース、移動、衝突、ラップ判定 | プラットフォーム非依存の計算ライブラリのみ |
| `pqpq-web` | `cdylib`によるWASMとJSバインディング、検証用`rlib` | ブラウザとの境界、予測・補正・補間、共有codec・simの呼び出し | protocol、sim、wasm-bindgen、必要なWeb APIバインディング |

client/server/webの3者がprotocolとsimに依存する。protocolとsimは互いに独立させ、アプリケーション層で通信DTOとsimのInputState・CarStateを変換する。これにより、通信形式の変更を物理計算から分離し、循環依存を防ぐ。

protocolとsimから上位3クレートへの依存は禁止する。simにはRatatui、Web API、quiche、ソケット、実時計、OS乱数、ファイルI/Oを持ち込まない。コース・物理定数・固定ステップはsimに1つだけ定義し、serverと両クライアントが同じコードを使用する。

```text
pqpq/
├── Cargo.toml                    Workspace resolver = "3"
├── Cargo.lock
├── crates/
│   ├── pqpq-client/
│   ├── pqpq-server/
│   ├── pqpq-protocol/
│   ├── pqpq-sim/
│   └── pqpq-web/
└── web/
    ├── index.html                参加・レース・結果の画面枠
    ├── app.js                    ブラウザI/OとWASMの接続
    ├── style.css
    └── pkg/                      生成するJSとWASM
```

`web/`は静的配布物のディレクトリであり、6個目のRustクレートにはしない。

クライアントのCargo.tomlには `[[bin]]` の `name = "pqpq"` と `path = "src/main.rs"` を設定し、パッケージ名と配布する実行ファイル名を分ける。

| 対象 | モジュール | 責務 |
| --- | --- | --- |
| client | `app` / `config` | 起動、画面状態遷移、終了、起動時設定の検証 |

## 3 クライアント外部仕様

### 3.1 CUI起動と共通入力値

```bash
pqpq foo 1234
```

| 入力 | 基本設計上の制約 | エラー時の扱い |
| --- | --- | --- |
| `username` | UTF-8で1〜48バイト。Unicode表示名を許可。制御文字、改行、端末制御文字、空白だけの名前は禁止 | 接続前に理由を表示して終了 |
| `room_id` | ASCII英数字、`-`、`_` の1〜32文字。大文字小文字を区別 | 接続前に理由を表示して終了 |
| 引数個数 | 必須位置引数は正確に2つ | 使用方法を表示して終了 |

名前と部屋IDの制約はWeb版にも同じ条件で適用し、サーバで必ず再検証する。Web版の入力エラーはフォーム上に表示して修正可能とする。

`RoomId` は文字列であり、`0012` と `12` は別の部屋とする。ユーザ名の重複は検査しない。同名プレイヤーは、画面上の短い識別表示と色・車両記号で見分けられるようにする。色だけに依存しない。

初期終了コードは、正常終了0、引数不正2、接続・プロトコル・端末エラー1とする。ユーザ名、接続先、部屋IDを設定ファイルや履歴ファイルへ書き戻さない。

### 3.2 接続先設定

通常利用は配布バイナリに設定した既定の接続先を使い、ユーザは名前と部屋だけを指定する。本番のホスト名は未確定であり、現時点で稼働中の接続先があるとは扱わない。開発版の既定値は `localhost:4433` とする。

開発・運用向けに環境変数で接続先、TLSサーバ名、信頼する開発用CAファイルを上書きできる設計とする。これらは必須引数を増やさず、アプリケーションによる設定の永続保存も行わない。

### 3.3 画面と状態遷移

```text
起動 → 接続中 → 待機室 → カウントダウン → レース → 結果 → 終了
               └─ 途中参加 → 観戦 ────────────┘
接続・通信エラー → エラー表示 → 終了
各画面 → 終了操作 → 終了
```

| 画面 | 表示内容 | 操作 |
| --- | --- | --- |
| Web参加画面 | 名前、部屋ID、JOIN、接続エラー | 入力、参加 |
| 接続中 | 接続状況、部屋ID、失敗理由 | 終了 |
| 待機室 | 部屋ID、参加者、識別表示、Ready状態、必要人数 | Ready、終了 |
| カウントダウン | 開始までの残り時間、参加者 | 終了 |
| レース | コース、車両、自車、周回、順位、速度、経過時間、RTT | アクセル、ブレーキ、左右、終了 |
| 観戦 | レース全体、順位、観戦中である旨 | 終了 |
| 結果 | 確定順位、完走時間、DNF、全員退出後に再作成できる旨 | 終了 |
| エラー | エラーの要点と再起動等の対処 | 終了 |

以下はCUIの表示例とする。Webも同じゲーム情報を表示するが、CanvasとHTMLで配置する。最終的な文字配置は端末サイズに応じて調整する。

```text
┌────────────────────────────────────────────────────────────┐
│ pqpq  ROOM 1234        LAP 2/3   POS 2/4   RTT 23ms         │
│                                                            │
│       ┌─────────────────────────────────────┐              │
│       │  A▶ foo                             │              │
│       │        ┌──────────────────┐         │              │
│       │        │                  │ B▶ foo  │              │
│       │        └──────────────────┘         │              │
│       └─────────────────────────────────────┘              │
│ SPEED 142 km/h    TIME 00:42.300    YOU B                    │
│ ↑ 加速   ↓ ブレーキ   ← → 操舵   q 終了                    │
└────────────────────────────────────────────────────────────┘
```

### 3.4 キー操作と端末対応

基本割当は、上矢印またはWをアクセル、下矢印またはSをブレーキ、左右矢印またはA/Dを操舵、EnterをReady、QまたはCtrl+Cを終了とする。左右同時入力は中立、アクセルとブレーキの同時入力はブレーキ優先とする。Readyは一方向の操作とし、初期版は解除キーを設けない。

キー解放イベントを取得できる端末では押下状態を保持する。解放通知が使えない端末では、押下・リピートから一定時間だけ入力を有効にする互換モードを用意する。期限の初期候補は200msとし、OSのキーリピート開始まで入力が途切れる可能性を実機検証する。互換モードでは画面に操作上の制約を表示し、端末対応表で区別する。キーの種類と端末側機能の条件は[CrosstermのKeyEventKind仕様](https://docs.rs/crossterm/latest/crossterm/event/enum.KeyEventKind.html)に従う。

最小画面サイズの初期値は80列×24行とする。サイズ不足時は拡大を促す表示に切り替え、ローカル入力を中立化する。フォーカス喪失を検知できる場合も同様とする。通信とゲーム進行は継続し、画面の都合で部屋を停止しない。

開始時にraw modeとalternate screenへ移行し、正常終了、エラー、Ctrl+C、可能な範囲のpanicで復元する。強制終了や端末プロセスの消失時は復元を保証しない。

### 3.5 URLからのWeb参加

本番URLの例は `https://<配置先ホスト>/` とする。URLを開くとHTML、JS、WASMを読み込み、名前と部屋IDの入力フォームを表示する。WASM初期化と通信機能の確認が完了したらJOINを有効にする。静的画面の閲覧だけでは部屋を作らず、JOIN成功時に初めて入室する。

部屋を共有するURLは `https://<配置先ホスト>/#room=1234` を設計案とする。フラグメントから部屋IDだけを事前入力し、名前は毎回入力する。URLには名前、PlayerId、認証情報を含めず、URLを開いただけでReadyにもならない。共有URLは招待権限や部屋予約を意味しない。

```text
Name  [ foo                  ]
Room  [ 1234                 ]
      [ JOIN                 ]
```

フォームはDOM、コースと車両はCanvas 2Dを初期方式とする。待機、Ready、カウントダウン、レース、結果の状態はCUIと共通である。Webでは明示的なReady・退出ボタンも提供し、入力欄へフォーカスしている間は文字入力を車両操作へ流さない。スマートフォンのタッチ操作は初期の必須範囲に含めず、キーボード操作可能なブラウザを対象とする。

### 3.6 ブラウザ境界と非表示時の扱い

DOM、Canvas、キーボード、WebTransportのI/Oは薄いJS層が担当し、バイナリcodec、車両予測、補正に使う状態管理はRust/WASM側で処理する。JS側に別の物理計算や勝敗判定を実装しない。u64の識別子・sequence・TickをJSのNumberへ変換せず、WASM内に保持するかBigIntまたは文字列で受け渡す。

描画はrequestAnimationFrame、予測は固定30Hzの時間蓄積方式とし、描画フレーム数を物理時間へ変換しない。ブラウザ停止からの復帰時に大量の古い入力をまとめて送らず、最新Snapshotを基準に再同期する。

blur、visibilitychangeによる非表示、操作領域のフォーカス喪失時には入力を中立化し、可能なら中立Inputを送る。送信できなくてもサーバの入力タイムアウトで中立化する。ページ終了時のLeave送信は保証せず、切断検出で退出を完了する。通信が生きていても非表示中のゲームはサーバで継続する。

読み込み直後にWebAssembly、WebTransport、secure contextを確認し、不足する場合は参加できない理由とターミナル版の利用案内を表示する。WebTransportの接続後にDatagram対応も確認し、要件を満たさない接続を別のゲームルールで参加させない。実際の対応ブラウザと版は相互運用試験で確定する。[WebTransportのAPI仕様](https://www.w3.org/TR/webtransport/)

## 4 部屋とレースのライフサイクル

### 4.1 参加処理

NativeではQUICハンドシェイク、WebではWebTransportセッション確立後、クライアントは専用の信頼性のある制御Streamの最初のメッセージとしてJoinを送る。サーバはプロトコル版、入力値、容量を検証してから、論理接続に一意なPlayerIdを割り当てる。

部屋検索、必要な部屋の生成、参加者登録を同一の状態所有者が連続して実行する。同じRoomIdへの同時Joinでも部屋を二重生成しない。検証に失敗した接続のために空の部屋を残さない。1接続につき1プレイヤー・1部屋とし、入室後の再Joinは拒否する。

### 4.2 部屋状態

| 現在の状態 | 契機 | 次の状態と処理 |
| --- | --- | --- |
| 存在しない | 最初の正常なJoin | Waitingの部屋を作成し、未Readyの走行予定者として登録 |
| Waiting | Join / Leave | 名簿を更新。カウントダウン中なら取消し、開始条件を再評価 |
| Waiting | 最少人数以上かつ全員Ready | Waitingの内部状態として3秒先の開始Tickを予約 |
| Waiting | 開始Tick到達、条件が引き続き成立 | グリッドと参加者を確定しRacingへ移行 |
| Racing | Join | 観戦者として登録。確定した出走者集合は変更しない |
| Racing | 全出走者が完走またはDNF | Finishedへ移行し結果を通知 |
| Racing | 制限時間到達 | 未完走者をDNFにしてFinishedへ移行 |
| Finished | Join | 結果閲覧者として登録し確定結果を返す |
| 任意 | 最後の接続が退出・切断 | 部屋と付随する結果を即時削除 |

カウントダウン予約時にRaceStartを送り、取消時にはRaceStartCancelledを送る。予約に `start_id` を付け、古い予約のSnapshotを受けても再開始しないようにする。待機室の人数変更時、既存プレイヤーのReadyは維持し、新規参加者は未Readyとする。

開始Tickでは、そのTickで受け付けたJoin/LeaveとReadyを先に反映して条件を再判定する。クライアント表示だけで開始を確定せず、サーバのRacing状態を正とする。カウントダウン中の車両入力は走行へ反映しない。

### 4.3 切断と結果保持

正常終了時はLeaveを送り、その後Native接続またはWebTransportセッションを閉じる。Leaveが届かなくても接続終了またはタイムアウトを契機として同じ退出処理を行い、二重処理を防ぐ。Web画面の再読み込みや別タブからの参加は新規接続として扱う。

レース中の未完走者が切断した場合はDNFとし、Playerと車両を直ちに削除する。結果表示に必要な出走時のPlayerId・表示名・完走またはDNF情報だけを、接続とは別のRaceEntryに残す。完走後の切断では完走記録を変更しない。これらも部屋削除時に破棄する。

残った走行者が1人になっても継続する。走行中の車両が0台になった場合は、観戦者が残っていれば結果へ移行し、誰もいなければ部屋を削除する。再接続は常に新規PlayerIdとなり、Racing中なら観戦扱いとする。

Finishedの結果は部屋に接続者がいる間だけ表示のために保持する。永続的な履歴にはしない。

## 5 ゲームルールとシミュレーション

### 5.1 コースと座標

初期コースは平面上の閉じた周回路とする。中心線、走行可能な幅、境界、順序付きチェックポイント、スタート兼ゴール線、スターティンググリッドを静的データとしてバイナリに同梱する。

静的コースと車両定数の唯一の定義元はpqpq-simとする。Web版にも同じ定義をWASM経由で渡し、JSやCSSにゲーム座標・物理定数を複製しない。

ゲーム座標はメートル、速度はm/s、角度はラジアン、時間は秒を単位とする。画面表示でのみ速度をkm/hへ変換する。コースの縦横比を保って端末セルへ写像し、端末上の文字幅・高さの差を描画側で補正する。

`course_id`、`course_version`、`physics_version` をJoinedで照合する。不一致時に異なるコースを表示したまま参加させない。コース寸法・チェックポイント座標・車両定数は詳細設計で確定する。

### 5.2 車両更新

全車両に共通の加速、制動、抵抗、最高速度、操舵特性、衝突半径を設定する。初期版は後退を設けず、速度の下限は0とする。サーバは固定時間幅 `dt = 1/30秒` で入力から速度・向き・位置を更新する。

コース外へ出る動きは境界位置へ補正し、境界方向への速度を減衰させる。車両同士は円形の当たり判定を基本とし、重なりの解消と速度調整をサーバで行う。完走またはDNFの車両は走行中の当たり判定から除外する。

判定順序はPlayerId順などの安定した順序とし、HashMapの列挙順に結果を依存させない。高速移動による境界・チェックポイントの通り抜けは、前Tick位置から現Tick位置までの移動区間で判定する。車両間についても連続判定または上限付きのサブステップを詳細設計で選定する。

simの入力は状態、操作、固定ステップ、明示的なコース・物理設定とし、出力は更新後状態と通過・衝突等のイベントとする。サーバは世界全体を更新し、クライアントは同じ運動関数を自車予測に使用する。浮動小数点計算のNative/WASM間のビット単位一致は前提にせず、共通テストベクトルの許容誤差とサーバ補正で整合を保つ。時刻・乱数が必要になった場合も外部から明示的に渡す。

### 5.3 周回と順位

スタート時の完了周回数は0とし、画面には走行中の周回を `1/3` と表示する。全チェックポイントを順番どおりに正方向へ通過し、ゴール線を正方向へ横切った時だけ完了周回数を増やす。スタート直後の線の通過、逆走、線付近の往復で周回を増やさない。

3周完了で完走とし、完走時間をサーバの開始Tickとの差とTick内の通過位置から計算する。順位は次の順序で決める。

1. 完走者は完走時刻の昇順とする。
2. 未完走の走行者は完了周回数、通過チェックポイント数、次チェックポイント方向への区間進捗の降順とする。
3. DNFは完走者・走行者より後に置き、DNF時点の進捗で並べる。
4. すべて同値ならPlayerIdの昇順とし、表示順を安定させる。

Tick内の完走時刻も同じ場合に同順位は設けない。接続中のプレイヤーだけを分母にすると切断で順位表示が変動するため、順位の分母は確定した出走者数を使用する。観戦者は順位に含めない。

### 5.4 サーバTick

各Tickでは以下を順番に処理する。`server_tick` はプロセス内で単調増加するu64とし、ゲーム状態はそのTickの更新完了時点を表す。

1. 入退室・Ready・切断通知を処理し、レースの状態遷移を判定する。
2. 接続ごとに受信した有効な最新InputStateを選ぶ。
3. 全走行車両の速度・向き・位置を更新する。
4. コース境界、車両間衝突、チェックポイントとラップを判定する。
5. 完走・DNF・順位・レース終了を確定する。
6. GameSnapshotを生成し、各接続の送信待ち領域へ渡す。

描画回数、受信パケット数、Inputの件数によって物理更新回数を増やさない。入力を大量送信しても加速や時間進行が速くならない。

## 6 実行モデルと負荷制御

### 6.1 サーバ

初期構成はTokio上のネットワーク処理と、全室のゲーム状態を単独で所有するゲームループで構成する。Roomを複数タスクから同時変更せず、通信タスクとの境界には上限付きのイベントキューと接続ごとの最新入力領域を使う。

Nativeのネットワーク処理はUDP受信をquicheへ渡し、制御StreamとDatagramを読み出す。送信可能なQUICパケットをUDPへ書き出し、quicheの期限でタイムアウト処理を呼ぶ。送信時刻の指示も扱う。quicheは低水準APIであり、ソケットI/Oとタイマーを含むイベントループはアプリケーション側の責務である。[quiche公式ドキュメント](https://docs.quic.tech/quiche/)

WebTransport側はHTTP/3セッションとそのStream・Datagramを処理し、Nativeと同じ内部イベントへ変換する。ゲームループでは接続元のUIを分岐条件にしない。HTTPS静的配信も別タスクとし、ファイル転送やWASMダウンロードがTickをブロックしないよう送信量と同時要求数を制限する。

ゲームループ内ではネットワーク送信完了を待たない。入力領域は最新値で上書きし、Snapshot送信待ちも最新状態を優先する。制御メッセージは順序を保つが、1接続の未送信量が上限を超えたらその接続を終了し、他接続を待たせない。

### 6.2 Tickの遅延

通常は約33.33ms間隔で1Tickを進める。遅延時の追い付き処理は1回の実行機会につき最大3Tickを初期値とし、以降はI/Oへ実行を譲る。追い付き中の中間Snapshotは送らず最新だけを配信する。

大きな遅延では過剰な追い付き処理を打ち切り、次回期限を再設定する。この場合も物理計算のdtは変えず、処理していないTick番号を飛ばさない。持続的な過負荷ではゲーム時間が実時間より遅れることを許容し、Tick遅延として観測する。レース制限時間・完走時間はシミュレーション時間、接続期限は単調時計による実時間で管理する。

Tokioのintervalには遅延後の挙動を選ぶ仕組みがある。既定動作に任せず、上記の回数制限をゲームループ側で明示する。[TokioのMissedTickBehavior仕様](https://docs.rs/tokio/latest/tokio/time/enum.MissedTickBehavior.html)

### 6.3 クライアント

端末イベント、通信、自車の30Hz予測・入力送信、60FPS目標の描画を分離する。Web版も同じ時間モデルを採用し、Tokio・quiche・CrosstermをWASMへ持ち込まない。描画には直近の状態を渡し、遅れた描画フレームは省略する。ブラウザ全体が停止した場合はサーバ側の時間進行を継続する。

## 7 通信設計

### 7.1 接続とチャネル

| 項目 | 設計 |
| --- | --- |
| Nativeトランスポート | UDP上のQUIC。quicheを使用し、ALPNは `pqpq/1` |
| Webトランスポート | WebTransport over HTTP/3。ALPNは `h3`、接続パスは `/transport` |
| 暗号化 | QUICのTLSによる通信保護。クライアント証明書による本人認証は行わない |
| サーバ確認 | NativeはTLS設定、Webはブラウザの信頼モデルで証明書・ホスト名を検証 |
| Native制御チャネル | クライアントが開く双方向Stream 0を1本使用 |
| Web制御チャネル | WebTransportセッション内に作る専用双方向Streamを1本使用。生のStream 0と同一視しない |
| リアルタイムチャネル | NativeはQUIC DATAGRAM、WebはWebTransport Datagrams。両方で非信頼配送への対応を確認 |
| 互換性 | transportのネゴシエーションと共通Joinのプロトコル版を照合。不一致は理由を表示して終了 |
| 再開 | ゲームのセッション復元なし。0-RTTによるJoin/Ready処理は使用しない |

認証を持たないという要件はユーザの本人認証を意味する。接続先サーバの証明書検証は有効にし、検証無効を通常の開発方法にしない。NativeのTLS設定は[quicheの証明書検証仕様](https://docs.quic.tech/quiche/struct.Config.html#method.verify_peer)に従う。ローカル開発にはlocalhost用の証明書と開発CAを使用し、Nativeとブラウザ双方が信頼するよう設定する。ブラウザ側の信頼条件は対象ブラウザで実接続して確認する。

WebTransportセッションはHTTP/3のExtended CONNECTとWebTransport用の設定交渉を含む。専用Streamの関連付けとDatagramのセッション識別はWeb adapterが処理し、そのヘッダーをゲームcodecへ渡さない。HTTP/3ライブラリを追加しただけでWebTransport対応が完成したとは扱わない。[IETF WebTransport over HTTP/3仕様案](https://datatracker.ietf.org/doc/html/draft-ietf-webtrans-http3)

Web adapterの実装ライブラリは詳細設計前の接続検証で選定する。quicheのHTTP/3 APIを採用する場合も、対象版がブラウザと相互運用するWebTransport機能を備えるか確認する。必要なら同じpqpq-server内に別のWebTransport実装を組み込む。別プロセスや外部ゲートウェイを前提にしない。

### 7.2 Transport抽象化

アプリケーションは内部 `ConnectionHandle` と以下の操作・イベントだけを扱う。Native QUIC接続1つ、またはWebTransportセッション1つを、1つの論理接続として登録する。複数セッションが基盤の接続を共有する場合もプレイヤーを混同しない。

| 区分 | 操作・イベント | 意味 |
| --- | --- | --- |
| 送信 | `send_reliable(handle, bytes)` | 順序を保持する制御メッセージ |
| 送信 | `send_unreliable(handle, bytes)` | 古い状態を待たない入力・Snapshot |
| 受信 | `Connected` / `ReliableReceived` / `UnreliableReceived` / `Disconnected` | 共通の接続・配送イベント |
| 制御 | `close(handle, reason)` | 該当する論理接続の終了 |
| 能力 | `max_datagram_payload(handle)` | transportヘッダーを除いたゲーム用本文の上限 |

これは概念インターフェースであり、Rust traitの具体的なasync境界は詳細設計で決める。エンコード済みの同じメッセージをどちらのadapterにも渡せることを条件とする。

### 7.3 メッセージ形式

Streamには `u32長のペイロードサイズ + メッセージ本体` のフレームを流す。長さフィールドはネットワークバイトオーダーとする。受信1回が1メッセージに対応するとは仮定せず、分割受信と連結受信を処理する。本文の上限は64KiBとし、長さ検証前にそのサイズのメモリを確保しない。

Datagramは1つごとにメッセージ種別・版と本文を持つ。Snapshotを分割する場合は後述の断片ヘッダーを追加する。バイナリ形式を採用するが、シリアライズライブラリ、フィールド番号、整数幅、浮動小数点表現は詳細設計で確定し、protocolの往復変換テストと既知バイト列の互換性テストで固定する。

### 7.4 クライアントからサーバ

| メッセージ | 経路 | 主な項目 | 処理 |
| --- | --- | --- | --- |
| Join | Stream | protocol_version、username、room_id、course_version、physics_version | 入室検証と初期状態の返却 |
| Ready | Stream | なし | Waitingの走行予定者をReadyにする。重複は無害に扱う |
| Input | Datagram | sequence、throttle、brake、steering | 接続にひも付く車両の入力として受理 |
| Leave | Stream | なし | 退出し接続を終了 |

`sequence` は接続ごとに1から始めるu64であり、入力サンプルごとに増加する。`steering` は-1、0、1のみ許可する。Inputには位置、速度、順位、完走宣言、任意のPlayerIdを含めない。

### 7.5 サーバからクライアント

| メッセージ | 経路 | 主な項目 | 用途 |
| --- | --- | --- | --- |
| Joined | Stream | player_id、room_id、role、名簿、room_revision、レース状態、server_tick、開始予約、コース・物理版、Tick周期、周回数 | 入室時の初期化。Finishedなら結果も付与 |
| PlayerJoined | Stream | player_id、username、role、room_revision | 名簿への追加 |
| PlayerLeft | Stream | player_id、reason、room_revision | 名簿からの削除 |
| ReadyChanged | Stream | player_id、ready、room_revision | 待機表示の同期 |
| RaceStart | Stream | start_id、start_tick、出走者、グリッド、room_revision | 開始予約と初期車両状態の通知 |
| RaceStartCancelled | Stream | start_id、reason、room_revision | 開始予約の取消 |
| Snapshot | Datagram | GameSnapshot、受信者のlast_processed_input | 描画と自車補正 |
| RaceFinished | Stream | 終了Tick、確定結果、room_revision | 最終結果の確定 |
| Error | Stream | code、利用者向けの短い理由、fatal | 入室拒否・操作拒否・プロトコル異常の通知 |

`ReadyChanged`、`RaceStartCancelled`、`Error` は上位要件の最低限のメッセージ群を補う。ServerMessageには信頼できない内部エラー詳細や秘密情報を含めない。

上表のStreamはReliable、DatagramはUnreliableを意味し、Native/Webで同じメッセージを使用する。UI種別は能力確認や診断には使えても、加速・最高速度・操舵・衝突・周回条件の分岐には使用しない。

### 7.6 StreamとDatagramの順序差

同一Stream上の制御イベントは送信順に扱うが、StreamとDatagramの到着順は一致しない。部屋の名簿・Ready・開始・終了を変更するたびに `room_revision` を増やし、Snapshotにも付ける。

クライアントは、自分が適用済みの制御情報より新しいrevisionのSnapshotを最大3世代まで一時保持し、対応する制御イベントを適用してから描画する。古いrevisionや適用済みTick以前のSnapshotは破棄する。Joined以前のSnapshotを使って画面や自車を初期化しない。Finished確定後は遅着したRacingのSnapshotで状態を戻さない。

### 7.7 入力欠落と新旧判定

Inputはキー変化時だけでなく30Hzで現在の全入力状態を送る。古いInputの再送は行わず、後続の新しいサンプルによって現在状態を伝える。

サーバは接続ごとに最大受信sequenceを記録し、重複・逆順のInputを破棄する。1Tickに複数届いた場合は最大sequenceの入力だけを使う。最後の有効入力から実時間250msまではその状態を維持し、それを超えたらアクセル・ブレーキ・操舵を中立にする。中立後も惰性と抵抗による物理計算は継続する。

Snapshotの `last_processed_input` は、状態更新に取り込んだ最新sequenceと、それ以前の破棄済み入力を含む処理済み境界を表す。単にネットワークへ到着しただけのsequenceを通知しない。古い境界値への後退は認めない。

### 7.8 Snapshotのサイズと欠落

Snapshotは毎回完全状態とし、初期版は差分圧縮を行わない。1パケット欠落後も次の完全Snapshotだけで再開できるようにする。ユーザ名は名簿の制御メッセージで送り、30HzのSnapshotには重複して載せない。

送信可能サイズはQUIC接続ごとに確認する。QUIC DATAGRAMのペイロード上限は接続条件に依存するため、固定のUDPサイズをそのままアプリケーション本文上限として扱わない。[quicheのdgram_max_writable_len仕様](https://docs.quic.tech/quiche/struct.Connection.html#method.dgram_max_writable_len)

Web側もWebTransportのDatagramサイズ上限とサーバadapter側の上限を確認し、小さい方に収める。WebTransport用ヘッダーの分だけNativeと本文上限が異なる場合がある。同じゲームSnapshotでも接続ごとに断片数を決める。

1Datagramに収まらない場合はアプリケーション側で分割し、`server_tick`、`room_revision`、`fragment_index`、`fragment_count` を付ける。同じTick・revisionの全断片がそろった時だけ採用する。断片の再送は行わない。

初期上限は1Snapshotあたり16KiB・16断片、同時復元3世代、復元期限250msとする。新しい完全Snapshotを採用したら古い断片を破棄する。欠落した世代を待って後続の採用を止めない。DATAGRAM未対応またはこれらの上限で必要な状態を配信できない接続は、理由を返して終了する。容量設定を引き上げる場合は、最大名簿サイズとSnapshotサイズも再評価する。

### 7.9 代表的な通信の流れ

```text
Terminal A                  Server                       Browser B
   |                          |<--- HTTPSで配布物取得 --------|
   |--- Native QUIC接続 ------>|<--- WebTransport接続 --------|
   |--- Join(foo,1234) ------->|                             |
   |<-- Joined(PlayerId=1) ----|<--- Join(foo,1234) -----------|
   |<-- PlayerJoined(2) -------|--- Joined(PlayerId=2) ------>|
   |--- Ready --------------->|<--- Ready -------------------|
   |<-- ReadyChanged ---------|--- ReadyChanged ------------>|
   |<-- RaceStart(T+90) -------|--- RaceStart(T+90) ---------->|
   |                          | 開始TickでRacingへ移行        |
   |--- Input(seq=N) --------->|<--- Input(seq=M) ------------|
   |<-- Snapshot(Tick,ack=N) --|--- Snapshot(Tick,ack=M) ----->|
   |            上記の入力・更新・配信を30Hzで反復             |
   |<-- RaceFinished ---------|--- RaceFinished ------------>|
   |--- Leave --------------->|<--- Leave -------------------|
   |                          | 最後の退出で部屋削除          |
```

## 8 予測と描画の同期

### 8.1 自車予測

クライアントは30Hzで入力をサンプルし、sequenceと入力を履歴へ入れ、同じサンプルで自車を1固定ステップ予測する。60FPS描画では予測状態間を滑らかに表示する。サーバの応答を待たずに自車の動きを表示するが、ラップ・順位・完走は予測で確定しない。

予測対象は基本の車両運動と静的コース境界とする。他車との衝突はサーバ結果で補正し、通信遅延のある他車情報を使って完全な衝突再現を保証しない。

### 8.2 Reconciliation

新しいSnapshotを採用した時は、次の手順で自車を補正する。

1. Snapshotに含まれる自車の位置・速度・向きを予測計算の基準状態にする。
2. `last_processed_input` 以下の入力を履歴から削除する。
3. 未処理の入力をsequence順に、各1固定ステップとして再適用する。
4. 新しい予測状態を論理状態へ即座に反映し、描画位置との差だけを短時間で解消する。

入力はサーバ側で最新値に集約されるため、再適用は遅延区間の近似であり、サーバとクライアントで同じsequenceが同じTickに適用されるとは仮定しない。Tickと処理済み境界を両方使って古いSnapshotを排除し、後続Snapshotで誤差を収束させる。

描画補正の初期値は100msとする。コース外表示を招く大きな誤差、開始、完走、履歴の欠落では補間せず正しい状態へ合わせる。大誤差の閾値は車両サイズとの関係で詳細設計する。入力履歴は最大120件とし、超過または状態更新の長期停止時は予測を止め、最新Snapshotから履歴を初期化する。

### 8.3 他車のInterpolation

他車は、受信したSnapshotのTickを使い、推定サーバ時刻から初期値100ms遅れた時刻を描画する。前後の位置・速度・向きを補間し、角度は短い回転方向を選ぶ。名簿、順位、周回は補間せずサーバ値を使用する。

サーバ時刻の推定はSnapshotのTick、受信時刻、補助Ping/Pongから得たRTTを基に緩やかに補正する。両クライアントで同じ推定方法を使い、Native QUICのRTT統計は診断用の補助情報とする。OSの実時計同期を必須にしない。起動直後など補間用の2状態がそろわない間は直近状態を表示する。

将来側の状態が欠けた場合、速度による外挿は最大100msまでとし、以降は直近の表示を固定して通信遅延を知らせる。受信再開時は新しい時系列へ戻す。補間バッファは最大1秒・30Snapshotを初期上限とする。

## 9 メモリ上のデータ設計

### 9.1 主要エンティティ

| データ | 主な項目 | 所有者と寿命 |
| --- | --- | --- |
| ServerState | rooms、next_player_id、server_tick、容量設定 | サーバプロセス |
| ConnectionState | Native接続またはWebTransportセッション、内部接続ハンドル、player_id、room_id、受信バッファ、期限 | transport。論理接続終了まで |
| Room | RoomId、players、race、room_revision | ゲームループ。最後の接続者退出まで |
| Player | PlayerId、表示名、role、ready、接続ハンドル、最新入力、入力時刻 | Room。退出まで |
| RaceState | Waiting/Racing/Finished、start_id、start_tick、course_id、出走者、結果 | Roomと同じ |
| RaceEntry | PlayerId、出走時表示名、状態、進捗、完走Tick・Tick内時間 | レース開始から部屋削除まで |
| CarState | position、velocity、direction、進捗、次チェックポイント | simの共通型。出走中。完走・DNFで走行対象から除外 |
| GameSnapshot | tick、room_revision、race_phase、開始予約、車両一覧、周回・順位 | 一時的な配信とクライアントの有界バッファ |
| ClientState | 自分のID、名簿、画面状態、予測履歴、補間バッファ | NativeプロセスまたはWebページのメモリ |

PlayerIdはプロセス内で再利用しない単調増加u64とする。枯渇時は新規参加を拒否し、折り返して再利用しない。サーバ再起動後の同じ数値との同一性は保証しない。

QUICのConnection ID自体をPlayerIdとして公開せず、transport側の内部接続ハンドルを介して対応付ける。通信先アドレスもゲーム上の本人識別には使わない。

### 9.2 Snapshotに含める情報

車両単位ではPlayerId、位置、速度、向き、完了周回数、順位、走行・完走等の状態を含める。受信者ごとの外側の情報として処理済み入力sequenceを付ける。サーバ内部の入力キュー、接続ハンドル、TLS情報、衝突判定用の中間値は送信しない。

### 9.3 永続化の境界

DB、ファイルへのゲーム保存、保存用キュー、スナップショット復元機構は持たない。終了した部屋・接続の参照を診断用に保持し続けない。

バイナリ内のコース・既定値と、運用者が用意するTLS証明書・秘密鍵はゲーム状態ではない。アプリケーションはこれらを読み込むが、ユーザ設定やゲーム情報を書き戻さない。TLS鍵、ユーザ名、RoomId、アドレス、メッセージ本文を通常ログへ出さない。

Web版でもCookie、localStorage、sessionStorage、IndexedDBへ名前・部屋・セッション・結果を保存しない。Service Workerによるゲーム状態の保存や再開も行わない。HTML・JS・WASM・CSSは配布物としてHTTPキャッシュ可能だが、プレイヤー情報を混ぜない。再読み込みでは未参加状態から始める。

## 10 エラーと保護設計

### 10.1 代表的な異常処理

| 事象 | サーバの処理 | クライアントの表示・動作 |
| --- | --- | --- |
| 名前・部屋ID不正 | Joinを拒否。部屋を作らない | 入力制約を表示して終了 |
| 接続不可・証明書不正 | 入室しない | 接続先または証明書の問題を表示して終了 |
| WASM読込・Web機能不足 | 部屋を作成しない | 読込失敗または非対応機能を表示し、再読込・対応環境を案内 |
| WebTransport交渉失敗・UDP遮断 | Native接続とは独立に対象セッションを終了 | Web接続の失敗を表示。HTTPポーリングへ切り替えない |
| バージョン・コース不一致 | Joinを拒否 | 対応するクライアントが必要と表示 |
| 容量超過 | `ServerFull` / `RoomFull` | 混雑または満室を表示して終了 |
| Join前の操作・2回目のJoin | プロトコル違反として終了 | 通信形式の不一致を表示 |
| 不適切なReady | 状態不正エラー。レースは継続 | 操作できない理由を表示 |
| 観戦者・完走者のInput | ゲームへ反映しない | 操作対象外の画面を維持 |
| 古いInput・Snapshot | 破棄 | 新しい状態を継続利用 |
| 入力欠落250ms超過 | 入力を中立化 | 通信遅延を表示 |
| 切断・無応答 | Playerを削除、必要ならDNF、空室を削除 | 接続終了を表示し、再起動による新規参加を案内 |
| 不正な長さ・値域・メッセージ | 長さを確認して拒否。重大または反復時は接続終了 | 通信エラーとして終了 |
| サーバ終了 | メモリ上の全状態を破棄 | 切断を表示。自動的な状態復元は行わない |

### 10.2 タイムアウトと上限

以下は基本設計上の初期値であり、ネットワーク試験で調整する。

| 対象 | 初期値 | 超過時 |
| --- | --- | --- |
| 接続確立 | 5秒 | 接続試行を終了 |
| 論理接続確立後のJoin待ち | 5秒 | 未参加接続・セッションを終了 |
| QUIC idle timeout | 10秒 | 接続終了として退出処理 |
| アプリケーション無応答 | 5秒 | 生存確認に応答がなければ接続終了 |
| 入力受信 | 持続60件/秒、短時間バースト120件/接続 | 超過を破棄。継続違反は切断 |
| 制御メッセージ受信 | 持続10件/秒、バースト20件/接続 | 継続超過で切断 |
| 制御Stream送信待ち | 256KiB/接続 | 遅い接続を終了 |
| 入退室等のイベント待ち | 1,024件/サーバ | 新規受付を抑制し、切断処理を優先 |

Waiting・Finishedでは操作がない状態が正常であるため、無応答判定には入力送信の有無を使わない。補助制御メッセージPing/Pongを1秒ごとに送り、各側は未応答nonceの期限で判定する。Ping/Pongはゲーム結果を変更せず、通常の制御受信上限に収まるよう送る。

未確立のQUIC接続にも別枠の上限を設け、Join前の接続が無制限にメモリを消費しないようにする。IP単位の接続試行制限、QUICのアドレス検証、Retryの導入条件はtransportの詳細設計で具体化する。共有回線利用者への影響を考慮し、IPアドレスを本人識別にはしない。

### 10.3 Web固有の検証

WebTransport接続では許可するWeb配信Originを完全一致で照合し、不明なOriginを拒否する。これはブラウザからの利用元を制限する処理であり、ユーザ本人認証の代用にしない。Native側には引き続きメッセージ・所属・頻度の検証を適用する。

表示名をHTMLとして解釈せず、DOMにはtextContent相当、Canvasには文字描画APIを使う。HTTPS配信は固定の配布ディレクトリ内に限定し、パストラバーサルや任意ファイル閲覧を拒否する。証明書と秘密鍵は配布ディレクトリ外に置く。アクセスログにURLフラグメント、入力した名前、Join本文を記録する仕組みは設けない。

Content Security Policyでスクリプトと接続先を必要な配信元へ限定し、選定ブラウザでWASM実行を許可する設定を検証する。1つのオリジンから提供する構成を基本とし、公開時に不要なワイルドカード許可を設けない。

## 11 開発と運用

### 11.1 ローカル開発

Dockerを必須にせず、1台のPCでサーバと複数クライアントを別プロセスとして起動する。以下は実装後の起動形であり、現在の雛形ではゲームは動作しない。

```bash
# Terminal 1
cargo run -p pqpq-server

# Terminal 2
cargo run -p pqpq-client -- foo 1234

# Terminal 3
cargo run -p pqpq-client -- foo 1234
```

ブラウザでは `https://localhost:8443/` を開き、同じ部屋IDを指定する。開発用証明書の信頼設定とWeb配布物の生成を先に済ませる。

Windows・Linux・macOSのNative版とWeb版を受入対象にする。対応するOS・端末・ブラウザの版はビルド・入力・WebTransport相互運用試験で確定する。Rust、外部クレート、ネイティブビルドツールの版は実装時に固定し、WorkspaceルートのCargo.lockを再現ビルドの基準とする。

### 11.2 WASMのビルドと配布

`pqpq-web`を `wasm32-unknown-unknown` 向けにビルドし、wasm-bindgenでブラウザ向けJSバインディングを生成する。初期版はバンドラーを必須にせず、ES Modulesとして配信する。[wasm-bindgenのブラウザ向けビルド例](https://wasm-bindgen.github.io/wasm-bindgen/examples/without-a-bundler.html)

ビルド基盤の具体的な準備・起動手順は[WebAssemblyのREADME](../web/README.md)に記載する。

```bash
rustup target add wasm32-unknown-unknown
cargo build -p pqpq-web --target wasm32-unknown-unknown --release
./target/wasm-tools/bin/wasm-bindgen target/wasm32-unknown-unknown/release/pqpq_web.wasm --target web --out-dir web/pkg
```

上記のCLIはREADMEの手順でプロジェクト内へインストールする。Windowsでは実行ファイル名を `wasm-bindgen.exe` とする。wasm-bindgenのRust依存とCLIの版を一致させる。WASMビルドの対象を `-p pqpq-web` に限定し、Nativeのソケットや端末依存をWASMへビルドしない。protocolとsimはNativeおよびWASMでビルドできることを確認する。

HTML・JS・CSS・WASMをひとまとまりで公開し、途中の版が混在しないよう配布する。HTMLは更新確認できるキャッシュ方針、内容ハッシュ付きアセットは長期キャッシュ可能とする。WASMのContent-Typeは `application/wasm`、JSはJavaScriptとして配信する。ゲームプロトコル・コース・物理版は接続時にも照合し、古いページには再読み込みを案内する。

Rustテストに加えて、同じ入力列をNativeとWASMで実行して状態を比較する。これはWASMへコンパイルできるだけでは確認できないため、Nodeまたはブラウザで生成物を実行する検証を含める。

### 11.3 起動時設定

環境変数名は以下を設計案とする。ゲーム実行中に設定を書き換える管理APIは設けない。

| 対象 | 変数 | 用途 |
| --- | --- | --- |
| client | `PQPQ_SERVER_ADDR` | 接続先ホストとポート |
| client | `PQPQ_TLS_SERVER_NAME` | 証明書検証に使用するサーバ名 |
| client | `PQPQ_CA_FILE` | 開発用CA。指定しない場合の信頼ルート取得方法は実装時に固定 |
| server | `PQPQ_BIND_ADDR` | 待受アドレス。開発既定はループバックのUDP 4433 |
| server | `PQPQ_WEBTRANSPORT_ADDR` | WebTransportのUDP待受。開発既定はループバックの8443 |
| server | `PQPQ_HTTPS_ADDR` | 静的配信のTCP待受。開発既定はループバックの8443 |
| server | `PQPQ_WEB_ROOT` | HTML・JS・WASMの配布ディレクトリ |
| server | `PQPQ_WEB_ORIGIN` | WebTransportで許可するWeb配信元。開発時は `https://localhost:8443` |
| server | `PQPQ_TLS_CERT` / `PQPQ_TLS_KEY` | サーバ証明書・秘密鍵のファイルパス |
| server | `PQPQ_MAX_CONNECTIONS` / `PQPQ_MAX_ROOMS` / `PQPQ_MAX_ROOM_PLAYERS` | 容量上限。部屋の上限には観戦者も含める |
| server | `PQPQ_MIN_RACERS` | 通常2。1人検証では1 |

証明書・秘密鍵の不足、不正な設定値、ポートの使用中は起動時にエラーとし、半端な状態で待受を続けない。秘密鍵本体を環境変数やリポジトリへ含めない。

ブラウザへは公開してよい接続URL・ゲーム版情報だけを配布し、サーバの環境変数全体を送らない。通常のWebTransport接続先はページと同じホストの `/transport` とする。

### 11.4 単一VMへの配置

VMではサーバを専用ユーザで実行し、Native用UDP 4433、WebTransport用UDP 443、HTTPS用TCP 443を初期構成として公開する。443のbind権限はOSの限定的な権限付与等で扱い、アプリケーション全体を管理者権限で動かす前提にはしない。プロセスの起動・停止・再起動はOSのサービス管理機能を利用できるが、ゲーム状態の復旧機能は付けない。

停止時は新規受付を止め、可能な接続には終了理由を通知する。正常停止の待機は最大3秒を初期値とし、保存処理を行わず終了する。再起動は空のServerStateから開始する。

### 11.5 観測

接続数、部屋数、Tick処理時間、Tick遅延、送受信量、Datagram破棄数、補正量、描画FPSをメモリ上で集計する。通常ログは起動・停止・エラー種別・匿名集計に限定し、標準出力または標準エラーへ出す。恒久的な監視基盤や履歴DBは初期構成に追加しない。

ログにユーザ名・部屋・レース結果を出さないことで、OSが標準出力を保存する環境でもゲーム履歴を残さない。検証用のネットワークキャプチャ等は通常運用から分離し、実データの永続保存を標準機能にしない。

### 12.3 性能とネットワークの検証

基準環境はCPU、メモリ、OS、端末、ビルド設定、接続人数、部屋数を記録する。まず同一PC上の2〜4人で正常系を確認し、1〜3人の想定利用と10人・20人の負荷を測る。CPU・メモリ・帯域の実測値がないため、VMの必要性能は本書では断定しない。

通常負荷では30Hz更新が継続し、Tick処理時間のp99が33.33ms未満であることを目標とする。描画は60FPSを目標とし、未達でもサーバの更新周期が変化しないことを確認する。20人時の性能低下は、要件どおり観測結果として記録する。

| 試験 | 初期条件例 | 判定する内容 |
| --- | --- | --- |
| 遅延 | RTT 50 / 100 / 200ms | 自車予測の反応、補正量、開始表示のずれ |
| 欠落 | 双方向に1 / 5 / 10% | 欠落Tickを待たず更新し、最新状態へ復帰する |
| ジッター | 片道遅延の変動±20ms | 補間枯渇、過大な外挿が発生しない |
| 順序逆転・重複 | 試験用転送器でDatagram順序を変更 | sequence・Tick・revisionが巻き戻らない |
| 一時停止 | 入力方向を300ms遮断 | サーバ入力が中立へ戻る |
| 切断 | プロセス強制終了・双方向通信遮断 | タイムアウト後にPlayerと空室が消える |
| 大きいSnapshot | 20人以上、送信上限を小さくする | 分割・復元・断片欠落後の後続採用が成立する |
| 描画遅延 | 小画面・低速端末・描画周期を低下 | ゲーム更新と通信を止めない |
| Web停止・復帰 | 別タブへ移動、画面ロック、長いフレーム停止 | 中立入力、期限処理、復帰時の再同期 |

遅延付与は開発OSで利用できるネットワーク制御機能または試験用UDP転送器を使い、Dockerを必須にしない。断片欠落後は新しい完全Snapshotから再開することを確認する。補正の収束時間と許容誤差は車両定数の確定後に定量化する。

Native・WebTransportのそれぞれに劣化を与える試験と、両者を同じ部屋へ混在させる試験を行う。HTTPの静的配信が成功してもWebTransport接続が成功したとは判定しない。

### 12.4 境界条件の検証

- 同じRoomIdへの同時Join、開始Tick直前のJoin/Leave、カウントダウン取消し。
- 全走行者の切断、観戦者だけが残る状態、Finishedへの新規参加。
- 逆走、ゴール線の往復、チェックポイント飛ばし、同Tickの複数完走。
- 不正UTF-8、制御文字、過大フレーム、範囲外操舵、Join前Input。
- 入力連打・送信過多でも1Tickあたりの移動量が増えないこと。
- StreamよりSnapshotが先着した場合、結果通知後に古いSnapshotが来た場合。
- 入力履歴上限、受信断片上限、遅い受信者、未確立接続の上限。
- サーバ再起動、証明書不正、端末縮小、Ctrl+C時の端末復元。
- 入退室を繰り返して部屋やバッファの参照が残り続けないこと。

### 12.5 クロスプラットフォームの受入

| 組み合わせ・対象 | 必須の確認 |
| --- | --- |
| Windows端末 + Browser | 同じRoomで開始し、3周完走と同一結果を確認 |
| Linux端末 + Browser | 同上 |
| macOS端末 + Browser | 同上 |
| Windows + Linux + macOS + Browser | 4クライアントが同じサーバの同じ世界へ参加 |
| Browser + Browser | 別タブ・別ブラウザで名前が重複しても別Playerとして競走 |
| NativeとWASMの共通入力列 | 同一のsimコード・定数で状態差が定義した許容誤差以内 |
| NativeとWASMのcodec | 同一メッセージが同じバイト列になり、相互復号できる |
| ブラウザ非対応・証明書不正 | 部屋へ参加せず理由を表示する |
| ブラウザ再読み込み | 旧Playerを復元せず、新規参加として扱う |
| 5クレートの依存 | sim/protocolが上位層へ依存せず、WASMへNative依存が混入しない |

クライアント種別ごとの性能調整で、加速度・最高速度・旋回率・衝突・ラップ条件を変更していないことを確認する。UIの違いは描画と操作の取得方法に限定する。

## 13 詳細設計で確定する事項

| 項目 | 確定する内容 | 判断に必要な確認 |
| --- | --- | --- |
| 本番接続先 | ホスト名、証明書発行・更新、VMの仕様 | 配置環境と運用手順 |
| 対応環境 | Windows・Linux・macOSの対象版、端末、ブラウザ版、キー解放方式 | Nativeビルド、端末実機、WebTransport相互運用 |
| WebTransport実装 | サーバライブラリと版、HTTP/3機能・設定、セッション制御 | ブラウザからのStream・Datagram往復 |
| ワイヤ形式 | シリアライズ方式、全フィールドの型・幅、タグ、エラーコード | 最大人数時のサイズと不正データ耐性 |
| 車両物理 | 加速度、最高速度、抵抗、操舵、衝突処理 | 30Hzでの安定性と操作感 |
| コース | 座標、幅、チェックポイント、最大出走人数分のグリッド | ショートカット防止と描画視認性 |
| 同期調整 | 補間遅延、描画補正閾値、許容誤差と収束時間 | 遅延・欠落・ジッター試験 |
| 制限値 | 接続・キュー・入力頻度・断片サイズ等の最終値 | 1〜3人および10人・20人の実測 |
| 依存ライブラリ | クレート版、ネイティブ依存、WASMツール、信頼ルートの取得方法 | Native/WASMでの再現ビルド |

これらを決める際も、5クレート、共有シミュレーション、CUIとWebの混在対戦、単一サーバ、QUICとWebTransport、メモリ内だけのゲーム状態、ユーザ本人認証なしという前提は変更しない。

## 14 初期実装と検証記録（2026-09-30）

初期実装は5クレートの構成を維持する。Native QUICにquiche 0.30、WebTransportにwtransport 0.7、WASMの生成にwasm-bindgen 0.2.129を使用する。解決済みの依存バージョンはCargo.lockに固定する。ワイヤ形式はprotocolの独自バイナリcodec、コース・車両定数・同期処理はsimに実装し、両クライアントで共有する。

サーバはHTTPSの静的配信と接続設定配信も担当する。公開運用では公開CAの証明書を使い、開発時は14日以内のECDSA証明書とWebTransportの`serverCertificateHashes`を使える。開発モードは`PQPQ_PIN_WEB_CERT=true`で明示的に有効化し、HTTPS経由で証明書のSHA-256を渡す。HTTPS自体の検証は無効化しない。Native側はRustのファイルAPIで証明書を読み込み、Windowsの日本語パスに対応する。

### 14.1 実施した検証

検証環境はWindows 11、Rust 1.98.1、Node.js 26.8.1、Playwright管理下のChromium。Nativeはdebugビルド、WASMはreleaseビルドを使用した。

| 対象 | 結果 |
| --- | --- |
| Workspaceテスト | 63件成功。別サーバを必要とするNative実通信試験1件は通常実行ではignoreし、受入スクリプトから実行 |
| 静的チェック | rustfmt、Clippyの警告をエラー扱いにした全target検査に成功 |
| Native/WASMの共有ロジック | 同じ入力列の計算結果を誤差1e-6以内で照合、Joinのバイト列も一致 |
| 混在対戦 | Chromiumの実WebTransportと製品のNative QUIC通信処理で同じ部屋へ同名参加し、2台とも3周完走。順位とミリ秒単位の確定タイムが一致 |
| 部屋の寿命 | 全員退出後に同じIDへ再参加すると新しい待機室になる。連続3回の入退室に成功 |
| 途中参加 | レース開始後の3人目は観戦として参加し、退出できる |
| 接続キャンセル | ハンドシェイク中にキャンセルし直ちに再接続しても、新しい接続が古い処理に上書きされず待機室へ到達 |
| Webの失敗表示 | WebTransportがない環境、およびWASMを404にした環境で、読み込み画面に停滞せず理由を表示 |
| 通信劣化 | Native/Web両方向へ5%欠落・片道25±20ms遅延・10%のパケットへ追加50ms遅延を付与した混在レースで、2台とも完走・同じ結果を受信 |
| Tick | 上記劣化試験の60秒集計で1,800 tick、late=0、reset=0、最大Tick処理時間647µs。仮想マシン上の性能保証やp99測定ではない |
| CUI実行 | Windowsの疑似端末で実行ファイルを起動し、待機室参加、EnterでReady、Qで終了、端末モード復元を確認 |

自動運転は受入試験だけに置き、通常のゲームにはNPCを追加しない。Native試験は正規の入力Datagramを送信し、ブラウザ試験はキーボードイベントを発生させる。位置・周回・完走結果の注入は行わない。

再現コマンドは[README](../README.md#検証)を参照する。実通信のスクリプトは`scripts/crossplay.mjs`、暗号化済みUDPパケットの劣化転送器は`scripts/udp-link.mjs`。各実行の結果JSON・サーバログ・画面PNGは`target/crossplay/run-*/`へ出力し、Gitには含めない。

### 14.2 残る環境受入

Linux/macOSの実機、異なるOSを同時接続した組み合わせ、各端末のキー解放方式、Chromium以外のブラウザ、OCI本番配置、公開証明書の発行・更新、10人・20人の負荷測定は未実施。実装とローカル受入の完了を、これらの環境での検証完了とは扱わない。配置先と対象環境が確定した後、12.3〜12.5に沿って確認する。
